# Woko v0.6.0 implementation plan

**Status:** Proposed implementation plan  
**Release type:** Workflow, authorization, and Google Drive reliability update  
**Baseline:** v0.5.1  
**Target:** v0.6.0

## 1. Release goals

Woko v0.6.0 will:

1. Add a restricted `WORKER` role for internal work execution.
2. Add lightweight internal procurement proposal tracking without turning Woko into a procurement or Finance system.
3. Allow users with the `PERSON_IN_CHARGE` role to create work orders.
4. Ensure every work-order participant can open the work-order Drive folder and files, subject to Google Workspace policy.
5. Make Drive transfer resilient when a selected file cannot be moved into the Shared Drive.
6. Offer both local upload and Google Drive selection anywhere an action accepts an attachment.
7. Remove free-standing evidence upload from the work-order detail card and show only evidence attached through a business action, especially progress updates.

## 2. Product decisions

### 2.1 Role and assignment model

`WORKER` will be a global application role, like `PERSON_IN_CHARGE` or `OVERSEER`. Assignment to a specific work order will remain a separate relationship.

- A user must have the global `WORKER` role before they can be assigned as a worker.
- Workers may be assigned only to `INTERNAL` work orders.
- `VENDOR` work orders must not contain worker assignments.
- A user may hold multiple global roles, but permissions for an action are evaluated from both the user's roles and their assignment on that work order.
- The existing PIC assignment remains the accountable owner of execution. A worker assists the PIC; a worker is not a second PIC.

Recommended participant model:

| Work-order responsibility | Eligible global role | Internal work | Vendor work |
| --- | --- | --- | --- |
| PIC | `PERSON_IN_CHARGE` | Required | Required |
| Worker | `WORKER` | Optional | Not allowed |
| Reviewer | `FACILITIES_MANAGER` or `ADMINISTRATOR` | Optional/default manager | Optional/default manager |
| Overseer | `OVERSEER` | Optional | Optional |

A person should not be assigned to more than one responsibility on the same work order. This preserves clear UI labels, notifications, and authorization behavior.

### 2.2 Worker permissions

An assigned worker may:

- View the internal work order.
- Open its Drive folder and attachments.
- Participate in discussions.
- Record a progress update only while the work order is `ACTIVE` and its workflow stage is `IN_PROGRESS`.
- Attach progress evidence as part of that progress update, using either a local file or Google Drive.

An assigned worker may not:

- Create vendor work or be assigned to vendor work.
- Change workflow stage.
- Mark work complete or submit it to `REVIEW`.
- Approve completion.
- Change due date, priority, condition, PIC, reviewer, worker list, or overseer list.
- Perform vendor proposal actions.
- Perform internal procurement proposal actions unless the user independently has the PIC or manager role and is authorized by that action's policy.
- Upload free-standing evidence outside a progress update.

The API, not only the UI, must enforce these limits. In particular, `POST /work-orders/:id/transitions` must never authorize a request only because the actor has `WORKER` or is assigned as a worker.

### 2.3 PIC work-order creation

Users with any of these roles may create work orders:

- `ADMINISTRATOR`
- `FACILITIES_MANAGER`
- `PERSON_IN_CHARGE`

A PIC creator does not gain manager authority over the created work order. All later actions continue to use their normal role and assignment rules.

A PIC may create either an `INTERNAL` or `VENDOR` work order. The normal participant validation still applies. The create form should default the current PIC as a selected PIC when practical, while allowing another eligible PIC to be selected.

### 2.4 Work type must be selected before execution participants

Move work-type selection to an earlier creation step, before participant selection.

Recommended creation sequence:

1. Basic information and work type.
2. Location.
3. Responsibility:
   - PIC for both work types.
   - Worker picker only when work type is `INTERNAL`.
   - Reviewer and overseers for both work types.
4. Schedule and plan.
5. Initial attachments, using local file or Drive.
6. Review and create.

If the user changes the type from `INTERNAL` to `VENDOR`, the form must clear selected workers and explain that vendor work does not use workers. The API must reject vendor creation payloads containing worker IDs even if a client bypasses the UI.

### 2.5 Internal procurement proposal boundary

Internal procurement is a sub-workflow attached to an `INTERNAL` work order. It does not replace the main internal stages:

```text
PLANNED → SCHEDULED → IN_PROGRESS → REVIEW → COMPLETED
```

Woko tracks whether a proposal was submitted through the external Finance process and records Finance's communicated decision. Woko does not perform purchasing, supplier management, inventory, invoicing, payment, or Finance approval.

Procurement statuses:

- `NOT_REQUIRED`
- `PROPOSAL_REQUIRED`
- `SUBMITTED`
- `APPROVED`
- `REJECTED`
- `REVISION_REQUIRED`

Expected transitions:

```text
NOT_REQUIRED → PROPOSAL_REQUIRED → SUBMITTED → APPROVED
SUBMITTED → REVISION_REQUIRED → SUBMITTED
SUBMITTED → REJECTED
REJECTED → PROPOSAL_REQUIRED
PROPOSAL_REQUIRED | SUBMITTED | REVISION_REQUIRED | REJECTED → NOT_REQUIRED
```

Clearing procurement to `NOT_REQUIRED` after it was required must include a reason. A rejected proposal remains visibly rejected until the PIC starts a revised proposal or an authorized manager clears the requirement.

### 2.6 Internal procurement permissions

PIC responsibilities:

- Mark procurement required and provide a reason.
- Update the procurement note.
- Attach a procurement proposal by local upload or Drive selection.
- Confirm that the proposal was submitted through the external Finance process.
- Revise and resubmit after `REVISION_REQUIRED` or `REJECTED`.

Facilities Manager and Administrator responsibilities:

- Perform the same requirement-management actions when operationally necessary.
- Record Finance's communicated decision: `APPROVED`, `REJECTED`, or `REVISION_REQUIRED`.
- Supply a required decision note.
- Correct or clear the procurement requirement with a required audit reason.

Workers and Overseers cannot change procurement status.

A PIC who is also a Facilities Manager should be allowed to record the Finance decision because authorization is role-based. The audit log will retain both submission and decision actors. If separation of duties becomes mandatory later, it should be introduced as a separate policy change rather than inferred from participant labels.

### 2.7 Procurement completion guard

An internal work order cannot move from `IN_PROGRESS` to `REVIEW` while procurement is unresolved.

Blocking statuses:

- `PROPOSAL_REQUIRED`
- `SUBMITTED`
- `REVISION_REQUIRED`
- `REJECTED`

Non-blocking statuses:

- `NOT_REQUIRED`
- `APPROVED`

A Facilities Manager or Administrator may override this guard only with an explicit reason. The override reason must be stored in the progress timeline and immutable audit event. Marking procurement required does not automatically change the work condition; PICs and managers continue to choose `ON_TRACK`, `AT_RISK`, or `BLOCKED` separately.

### 2.8 Attachment policy

Every action that accepts an attachment must offer the same two source choices:

- Upload from device.
- Choose from Google Drive.

This applies to:

- Initial evidence during work creation.
- Internal progress updates.
- Completion submission.
- Vendor proposal documents.
- Internal procurement proposal documents.
- Any future action-specific attachment input.

The work-order detail `File evidence` card becomes a read-only attachment list with an **Open folder** action. It must not contain a generic evidence-type selector or upload control.

Evidence must be attached through the action it supports. A progress file appears under its progress update, a proposal document under its proposal record, and completion evidence under the completion submission/review history.

## 3. Data model and migrations

Add migrations after `0014_user_preferred_locale.sql`.

### 3.1 Application role

Add `WORKER` to `app_role`:

```sql
alter type app_role add value if not exists 'WORKER';
```

Update shared domain role types, administrator user management, reference-data responses, role labels, and role tests.

### 3.2 Work-order workers

Create `work_order_workers`:

```text
work_order_id  uuid FK work_orders, on delete cascade
user_id        uuid FK users
added_by       uuid FK users
added_at       timestamptz
primary key (work_order_id, user_id)
```

Add an index on `user_id`. Validate at the service layer that:

- the work order is `INTERNAL`;
- the user is active and has `WORKER`;
- the user is not also assigned as PIC, reviewer, or overseer on the same work order.

Include workers in work-order detail queries, `my work` filtering, discussion access, notifications, reports where participant filtering is intended, and Drive permission synchronization.

### 3.3 Internal procurement proposal

Create one current-state record per internal work order, for example `internal_procurement_proposals`:

```text
work_order_id          uuid PK/FK work_orders, on delete cascade
status                 internal_procurement_status
requirement_note       text nullable
submitted_by           uuid nullable FK users
submitted_at           timestamptz nullable
decided_by             uuid nullable FK users
decided_at             timestamptz nullable
decision_note          text nullable
version                integer not null default 1
created_at             timestamptz
updated_at             timestamptz
```

Create the row lazily when procurement is first marked required, or create a `NOT_REQUIRED` row when an internal work order is created. Creating the row with the work order is preferred because it simplifies detail queries and transition guards.

Retain complete history in `audit_events` and `progress_updates`; do not overwrite history when the current-state row changes.

Proposal attachments continue to use `attachments.evidence_type = 'PROPOSAL'`. Add an explicit association from the attachment to the internal procurement action or proposal record so vendor and internal proposal documents can be queried without relying only on evidence type.

### 3.4 Action-bound attachment lifecycle

The current attachment endpoints immediately create a `FILE_EVIDENCE_ADDED` timeline item before the related progress action is submitted. Replace that behavior with an action-bound lifecycle.

Recommended model additions to `attachments`:

```text
status                PENDING | ATTACHED
pending_action_token  uuid nullable
attachment_context    INITIAL | PROGRESS_UPDATE | VENDOR_PROPOSAL |
                      INTERNAL_PROCUREMENT | COMPLETION
attached_at           timestamptz nullable
```

Behavior:

1. Local upload or Drive transfer creates a `PENDING` attachment owned by the current user and returns its ID/token.
2. The related business action validates ownership, work order, context, and expected version.
3. The action atomically changes the attachment to `ATTACHED`, stores its relationship in structured data or a normalized join, and creates one timeline/audit record for the business action.
4. Work-order detail queries exclude pending attachments.
5. A scheduled cleanup removes expired pending records and their Drive files after a safe retention period, such as 24 hours.

This avoids orphan timeline entries and ensures the evidence list contains only files actually submitted with an action.

If this lifecycle is judged too large for v0.6.0, the minimum acceptable alternative is to stop creating `FILE_EVIDENCE_ADDED` timeline entries and hide unreferenced attachments from detail responses, with a cleanup job for unreferenced files.

### 3.5 Drive sharing state

Add operational fields or a dedicated table to track participant permission synchronization, for example:

```text
work_order_id
user_id
email
permission_id nullable
access_role
sync_status    PENDING | COMPLETE | FAILED | REMOVED
last_error nullable
updated_at
```

A normalized table is preferred because participants can change after folder provisioning. Permission failures must not silently disappear.

  - recording external Finance submission;

## 5. API plan

### 5.1 Authorization helpers

Add explicit helpers rather than expanding `requireManager`:

- `requireWorkOrderCreator`: Admin, Facilities Manager, or PIC.
- `isAssignedWorker(workOrderId, userId)`.
- `canRecordProgress`: manager, assigned PIC, or assigned worker under the worker restrictions.
- `canManageProcurement`: assigned PIC or manager.
- `canDecideProcurement`: Facilities Manager or Administrator.
- `canViewWorkOrder`: include assigned workers.

`POST /work-orders` should use `requireWorkOrderCreator`. Manager-only routes must remain manager-only.

### 5.2 Work-order creation and participant changes

Extend creation and participant payloads with `workerIds`.

Server validation:

- `workerIds` defaults to `[]`.
- Workers require `workType = INTERNAL`.
- Every selected worker is active and has `WORKER`.
- No duplicate person across PIC, worker, reviewer, or overseer responsibilities.
- A PIC creator is allowed, but participant role eligibility is unchanged.

Participant updates must synchronize:

- worker rows;
- assignment/removal notifications;
- timeline and audit detail;
- Drive folder permissions.

### 5.3 Progress update endpoint

Keep `POST /work-orders/:id/progress-update`, but update authorization:

- Manager: allowed during `IN_PROGRESS`.
- Assigned PIC: allowed during `IN_PROGRESS`.
- Assigned worker: allowed only for `ACTIVE`, `INTERNAL`, `IN_PROGRESS` work.

The endpoint remains a non-transition action. It must reject any attempt to submit completion, target another stage, or use completion evidence context.

The progress payload should accept finalized pending attachment IDs with `PROGRESS_UPDATE` context. At least zero attachments are allowed unless product policy later makes evidence mandatory.

### 5.4 Transition endpoint

`POST /work-orders/:id/transitions` remains limited to managers and assigned PICs according to existing workflow policy.

Add safeguards:

- Assigned workers are never accepted as transition actors.
- Internal `IN_PROGRESS → REVIEW` checks procurement status.
- Manager override requires `procurementOverrideReason`.
- Only attachment IDs with the correct completion context can be linked to review submission or completion approval.

### 5.5 Internal procurement routes

Recommended routes:

```text
POST /work-orders/:id/procurement-proposal/require
PATCH /work-orders/:id/procurement-proposal
POST /work-orders/:id/procurement-proposal/submit
POST /work-orders/:id/procurement-proposal/decision
POST /work-orders/:id/procurement-proposal/clear
```

Rules:

- Only `ACTIVE`, `INTERNAL` work orders are accepted.
- Require expected work-order version and procurement-record version where applicable.
- Submission requires at least one attached `PROPOSAL` document with `INTERNAL_PROCUREMENT` context.
- Submission UI and API record confirmation that submission happened outside Woko.
- Decisions are Manager/Admin only and require a note.
- Clearing requires a reason.
- Every state change creates a timeline update, audit event, and notification.

Suggested event types:

- `PROCUREMENT_REQUIRED`
- `PROCUREMENT_NOTE_UPDATED`
- `PROCUREMENT_PROPOSAL_SUBMITTED`
- `PROCUREMENT_PROPOSAL_APPROVED`
- `PROCUREMENT_PROPOSAL_REJECTED`
- `PROCUREMENT_PROPOSAL_REVISION_REQUIRED`
- `PROCUREMENT_NO_LONGER_REQUIRED`
- `PROCUREMENT_REVIEW_OVERRIDE_USED`

### 5.6 Attachment endpoints

Provide one shared API contract for both source types and all action contexts:

```text
POST /work-orders/:id/attachment-drafts/upload
POST /work-orders/:id/attachment-drafts/drive-transfer
DELETE /work-orders/:id/attachment-drafts/:attachmentId
```

Both create pending attachments. Business-action endpoints finalize them.

Authorization is context-specific. For example, a worker may create a `PROGRESS_UPDATE` draft during `IN_PROGRESS`, but cannot create an `INTERNAL_PROCUREMENT`, `VENDOR_PROPOSAL`, `INITIAL`, or `COMPLETION` draft unless another role grants that permission.

### 5.7 Approval queue

Extend `GET /approvals` with a separate collection:

```text
internalProcurementReviews
```

It lists internal proposals in `SUBMITTED`, separately from vendor proposal approvals and completion reviews. Include work order, submitter, submission date, requirement note, proposal documents, and decision eligibility.

### 5.8 Notifications

Recommended recipients:

- New work order: PICs, internal workers, reviewer, and overseers.
- Worker added/removed: affected worker and PICs.
- Worker progress update: PICs and reviewer/Facilities Managers as configured.
- Internal proposal submitted: Facilities Managers and Administrators.
- Finance decision recorded: PICs, workers, reviewer, and relevant overseers.
- Procurement requirement added or cleared: PICs, reviewer, and managers.

Deduplicate recipients when one user has multiple roles or assignments.

## 6. Google Drive reliability plan

### 6.1 Participant folder access

After the work-order folder is provisioned, synchronize access for every involved active user:

- creator;
- all PICs;
- internal workers;
- explicit reviewer;
- overseers.

Use Drive API `permissions.create` on the work-order folder with `supportsAllDrives: true`, `type: user`, and the participant's registered email. Use the least privilege that satisfies viewing and opening files; default to `reader` because Woko performs file writes through the API. Do not grant access to the entire Shared Drive unless Workspace policy requires it and that broader access is approved.

When participants change:

- add permissions for newly involved users;
- remove direct permissions for users no longer involved, unless they still receive access through another role or inherited group membership;
- record sync success or failure;
- retry transient failures through the job queue;
- show managers a warning when Drive access is not synchronized.

Important limitation: Google Workspace and Shared Drive policy can forbid direct sharing to non-members. The implementation cannot bypass an administrator policy. Before release, verify that the production Shared Drive allows item/folder-level sharing to users in `millennia21.id`. If it does not, choose one of these operational policies:

1. automatically add involved users as Shared Drive members, which grants broader access and is not preferred; or
2. use a Workspace group dedicated to Woko participants and manage membership; or
3. change the Shared Drive policy to permit limited folder sharing.

The preferred approach is direct work-order folder permission because it limits access to relevant work.

### 6.2 Move/copy fallback

The current Drive transfer uses the user's OAuth token for both move and copy. A user who cannot see or write to the Shared Drive destination can therefore fail at both operations.

Implement this ordered strategy:

1. Ensure the current participant's folder permission is synchronized before opening or completing Drive transfer.
2. Read source metadata and capabilities using the user's OAuth token.
3. If the file is owned by the user and can move into the Shared Drive, move it.
4. Otherwise, request explicit copy confirmation.
5. After confirmation, attempt a user-token Drive copy.
6. If the copy fails because the user cannot write to the destination, perform a server-mediated copy:
   - for binary files, download with the user's token and upload with the service account;
   - for Google-native files, temporarily grant the service account access to the source and copy it into the Shared Drive, then remove the temporary permission;
   - if temporary sharing is prohibited, offer an explicit exported-copy fallback using an appropriate format and clearly label that the stored file is an exported copy.
7. Preserve source file ID, transfer mode, original name/MIME type, resulting name/MIME type, and any conversion in attachment metadata and audit data.
8. Roll back the destination file if the database transaction fails.

Never silently convert a Google-native file. The confirmation must distinguish:

- moving the original;
- creating a native Drive copy;
- creating an exported copy such as PDF, DOCX, XLSX, or PPTX.

### 6.3 Drive permission and transfer errors

Return actionable error codes rather than a generic invalid-file response, including:

- `DRIVE_FOLDER_ACCESS_PENDING`
- `DRIVE_FOLDER_SHARING_NOT_ALLOWED`
- `DRIVE_MOVE_NOT_ALLOWED`
- `DRIVE_COPY_CONFIRMATION_REQUIRED`
- `DRIVE_NATIVE_COPY_NOT_ALLOWED`
- `DRIVE_EXPORT_CONFIRMATION_REQUIRED`
- `DRIVE_SOURCE_SHARING_NOT_ALLOWED`
- `DRIVE_TRANSFER_FAILED`

Do not log OAuth tokens or file contents. Audit only IDs, modes, actors, timestamps, and safe error summaries.

## 10. Risks and mitigations

| Risk | Mitigation |
| --- | --- |
| Shared Drive policy forbids folder-level sharing | Verify policy before implementation; document group or membership fallback. |
| Adding users as Shared Drive members exposes unrelated work | Prefer direct work-order folder permissions and least privilege. |
| User-token copy cannot write to the Shared Drive | Use service-account-mediated binary upload or native copy after temporary source sharing. |
| Google-native file cannot be copied due to source policy | Require explicit export fallback; retain audit metadata and never silently convert. |
| Pending uploads leave orphan Drive files | Add status, expiry, cleanup job, and transaction rollback. |
| Worker accidentally gains PIC powers through shared helpers | Use separate authorization helpers and negative API tests for every restricted action. |
| PIC creation is mistaken for manager authority | Keep create authorization isolated; do not expand manager checks. |
| Procurement status blocks legitimate completion | Provide manager override with mandatory reason and audit trail. |
| Role/participant overlap creates ambiguous permissions | Reject duplicate responsibility assignments for a work order. |
| Creation succeeds but initial attachments fail | Return the created work order, show partial-success recovery, and preserve idempotency. |
